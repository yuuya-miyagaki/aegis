## 1. 北極星（確定・grill 済み）

**非エンジニアのユーザーが、クライアント対応〜保守まで一気通貫で「崩れない非スラップ」を作れるようにする。**

**役割分担（grill-premise で確定）:**
- **harness（aegis）の役割** = ライフサイクルの構造化・段階的情報開示・ゲート強制・「非エンジニアに分かる形での可視化」。
- **LLM の役割** = 判断レベルの品質レビュー（部分は崩れてないか／構造的に崩れてないか／全体として問題ないか）を外部レビュアーとして担い、ユーザーの弱い開発チェックを補う。
- ∴ 「harness が品質を注入する」のではなく「賢い LLM に正しく働かせ・段階開示で迷わせず・結果を非エンジニアが判断できる形に出す」。aegis v1.0.0 命題（モデルが賢くなった）と整合。

## 2. ライフサイクル能力チェックリスト（監査の主評価軸）

各能力について「実装されているか／薄くないか／役割分担が実現しているか」を判定する。

**Client mode（上流・お客様と相対）**
1. クライアントから情報を引き出す（"決めるべきこと"の提示）
2. 仕様駆動開発に渡せる**仕様**を作り切る
3. ↑のためのサポート体制が harness 内にある（**絶対条件**）
4. LLM が迷わぬよう**段階的に情報開示**される

**Dev mode（仕様→実装）**
5. LLM が**部分/構造/全体**の健全性を精査（ユーザー代行の外部レビュー）
6. 機械的に正しい＋**完成仕様を遵守**する
7. 開発中のクライアント要望を**巻き取る**（変更管理）

**Client mode（納品）**
8. 成果物の説明 / 9. マニュアル作成 / 10. UAT / 11. 納品

**保守**
12. 運用で問題が出たら直せる

> grill で「全ライフサイクルは広すぎる前提では」と指摘したが、ユーザーは意図的に全ライフサイクルを狙う。よって"広さ"は論点でなく、上記12能力の**実装の厚み**と**役割分担の実現度**を1つずつ検証することが監査の仕事。

## 3. 監査の2層構造（順序：機械層 → 哲学層）

**層1：機械的健全性（客観・検証可能・並列サブエージェント向き）**
- tier 0-3 eval / `check_framework_contract.py` / `check_reference_drift.py` / 全テスト（現状 195・全 green が基準）
- subsystem 別構造レビュー：`hooks/`(+`lib`)・`scripts/`・`.claude/agents/`・`.claude/skills/`・`.claude/rules/`・`templates/`・`bin/`
- 観点：パス疎通／root↔example の IDENTICAL・同期／参照 drift／dead code／「テストが壊れたら検知できる構造か」／コードの実バグ

**層2：哲学/設計の妥当性（比較・判断・grill）**
- aegis の哲学を1枚に抽出（薄いカーネル／段階的開示／evidence ベース完了／ゲート強制／Client-Dev 分離 等）
- 最新フレームワークと対比（§4）
- **grill-premise / grill-plan で「12能力を満たす設計か・役割分担は正しいか・前提に穴はないか」を攻める**

順序の理由：壊れた土台の上で哲学を論じても無駄。先に「健全」を確定 → 思想を精査。

## 4. 調査方針（重要：ローカルコピーは古い）

ワークスペース直下の `superpowers-main/` `gstack-main/` `claude-code-best-practice-main/` `everything-claude-code-main/` `ultra-framework-v7/` `ultradesign-framework-v2/` は**古いスナップショット**。比較は**必ず最新版を web で調査**する（WebSearch / firecrawl / context7）。
- 既知の比較対象の**最新版**: Superpowers、GStack、Claude Code 公式ベストプラクティス、その他 agent/harness フレームワーク。
- **新興フレームワーク/ハーネスの探索**も行う（2026 時点で評価の高い agentic harness・spec-driven dev・lifecycle framework 等）。
- ローカルコピーは「過去にどう考えていたか」の参考に留め、評価の正は最新版。

## 5. 出力と完了条件

- 成果物：**重大度ランク付き監査レポート**（`docs/audit-report-<date>.md` を想定）。発散防止のため必ず1本の文書に集約。

- **完了条件**：12能力それぞれに判定と根拠がつき、機械層の重大度別所見が出揃い、推奨アクションが優先度付きで並ぶこと。

## 6. 境界（重要）

- **「監査（今あるものが健全か）」と「再設計（哲学/構造を変えるか）」を分離する。** 監査が黙って書き直しに化けないこと。再設計が要ると判明したら、別途 brainstorm→設計→grill→実装の通常フローに乗せる（監査レポートはそのインプット）。
- 監査自体は**読み取り・検証・記述**に徹し、コード変更はしない（変更は別タスク）。

## 7. grill-premise で既に pressure-test 済みの論点（再利用）

- 「ハーネスがエンジニア知識の欠如を埋める」は半分のみ成立 → 検証可能スラップは防げるが構造的スラップ（悪い抽象・密結合）はプロセスで注入不可 → **LLM のレビューで補う**と決着（§1 役割分担）。
- 「弱いチェックを harness が補う」前提はモデル進化で陳腐化しかけ → harness は「強制」から「正しく働かせ・可視化する」へ → §1 で再定義済み。
- 未検証の仮説（監査で確認）：実案件の規模/寿命（"大規模で崩れない"が YAGNI でないか）、"非スラップ"の最終ジャッジ者、「崩れない」の測定方法。
