# Aegis 行動レビュー charter（2026-06-11）

対象: Aegis v1.5.2（tag 済み・ローカル）
種別: **行動レビュー（behavioral review）** — 過去3レビュー（静的全力監査 2026-06-06／機能整合性監査 2026-06-07／進化レビュー 2026-06-10）で唯一未実施の「実運転の体験軸」を検証する第4のレビュー。
位置づけ: **監査と再設計の分離**（audit-charter-2026-06-06 §6 を踏襲）。本レビューは検出と提言のみを行い、実装・修正は行わない。

---

## 1. 目的と問い

- **問1（思想検証）**: 北極星——非エンジニアが Client→Dev→納品→保守の12能力を「崩れない非スラップ」で一気通貫できる——が、**実運転の体験として**成立するか。
  - コードレベルの正しさ（hook の発火・契約・mirror）は過去3レビューで検証済み。本レビューの新規性は「**段階開示・ゲート・judge 可視化・エビデンス完了が、実セッションの連なりの中で思想通りに振る舞うか**」を初めて観測すること。
- **問2（進化提言）**: 実走で得た一次情報をもとに、進化レビュー（2026-06-10）の E1〜E6 を再評価し、次のロードマップを提言する。

## 2. 評価正典

ユーザー確認済み（2026-06-11）: 既存文書を正典とし、文書化されていない期待との乖離が見つかればそれ自体を「文書化漏れ」として所見に記録する。

1. **北極星12能力**（Client上流①〜④／Dev⑤〜⑦／Client納品⑧〜⑪／保守⑫）
2. **役割分担**: harness=構造化・段階開示・ゲート強制・非エンジニア可視化、LLM=判断レベルの品質レビュー。「harness が品質を注入する」誤前提に戻らない
3. **3層トリアージ**: 保証=決定論 hooks／手順=skills／揮発値=隔離
4. **エビデンスなき完了なし**（Completion Rule）

### 3.2 題材

ピラティススタジオ「Studio Lift」の 1 ページサイト＋予約フォーム。クライアント＝スタジオオーナー（非エンジニア）。Hair Salon Bloom と独立した新規題材。

### 3.3 ペルソナ規約（レビュアーのエンジニア知識漏出の防止）

運転プロンプトは「非エンジニアの発注者兼運転者」を厳守する:

- 技術用語を使わない（「ゲート」「hook」「コミット」等はハーネス側が言い出すまで使わない。言われた語の復唱は可）
- コード・diff を読まない。ファイルパスを自分から指定しない
- 画面・出力に見えるものにだけ反応する
- ハーネスの指示が理解できない時は「分からない」と正直に言う（理解できないこと自体が所見）
- 各プロンプトは本 charter の脚本（§3.4）の意図に沿ってその場の文脈で書くが、上記規約を破らない

### 3.4 セッション脚本（〜15セッション）

| # | フェーズ | 運転内容 | 検証対象能力 |
|---|---------|---------|------------|

| 3 | Client: scope→acceptance→handover | 要件確定〜`client_ready_for_dev` 承認まで | ②④ ゲート体験 |
| 4 | Dev: brainstorm→plan | 開発計画 | ④段階開示 ⑤ |
| 5-6 | Dev: implement | サイト＋予約フォーム実装（TDD backstop 下） | ⑥機械的正しさ＋仕様遵守 |

- セッション境界＝実運用の「日をまたぐ」を再現（セッション復帰・STATUS 参照整合の検証点）。
- 進行が脚本とずれた場合: ハーネスの誘導に従うのを優先し、ずれ自体を観測として記録（脚本への強制復帰はしない）。

### 3.5 ストレスイベント定義

| ID | 投入点 | 内容 | 問うもの |
|----|--------|------|---------|
| S1 | requirements | 曖昧・矛盾・前言撤回するクライアント | ハーネスは「仕様を作り切る」②を構造で支えるか、LLM の機転任せか |
| S2 | implement 中 | スコープ拡大の変更要求 | ⑦変更管理が構造（要件更新→ゲート巻き戻し等）として機能するか |
| S3 | 保守 | 運用問題（フォームの不審メール＝スパム/abuse の疑い） | ⑫保守ルートが存在し、非エンジニアに次の一手を示せるか |

判定: 各イベントを「**構造で受け止めた**（hooks/ゲート/テンプレートが誘導）／**LLM 任せ**（モデルの良識で乗り切った）／**崩れた**（迷子・破壊・虚偽完了）」の3値で記録。

## 4. 観測プロトコル

### 4.1 機械観測（各セッション後に実施）

- ゲート状態: `docs/STATUS.md` の gate_approvals／`update-gate.sh` の挙動
- hook 発火痕跡: transcript 中の hook 出力・ブロックメッセージ
- evidence: `docs/qa-reports/` 等の成果物実在
- 整合: `python3 scripts/check_status.py --strict` の結果
- git log（sandbox 側）
- 観測ログは report の付録に再現手順付きで記録

### 4.2 体験観測（非エンジニア judge subagent）

主要チェックポイント（gate 承認時・judge card 表示時・マニュアル/UAT・各ストレス後）で、**ユーザーに見えるものだけ**（セッション出力・judge card・STATUS・マニュアル）を専用 subagent に渡し、技術文脈なしで評価させる:

1. いま何が起きているか説明できるか
2. 次に自分が何をすべきか分かるか
3. この承認（または差し戻し）判断を自信を持ってできるか
4. 分からない語・不安な点はどこか

### 4.3 採点 rubric

- **12能力 × {🟢思想通り／🟡部分的／🔴乖離／⚪未観測}**。全判定に証跡パス（transcript 行・ファイル）と再現手順を必須化
- **横断4軸**: 役割分担／3層トリアージ／段階開示／エビデンス完了 — それぞれ実走全体を通した総評＋証跡
- **ストレス3値**（§3.5）

## 6. 安全制約・予算

- aegis repo: **docs 追加のみ**。コード変更なし・push なし・tag 操作なし
- sandbox: `/tmp` 配下・使い捨て・実デプロイなし（deploy ゲートは実行せず挙動観測のみ。必要なら skip ルートを使う）
- 予算: 運転セッション上限 15＋smoke。Phase 0 でコスト感を実測し、超過見込みが出た時点でユーザーに報告
- 中断・再開: 各セッション後に観測を記録するため、任意の境界で中断・再開可能

## 7. フォールバック

Phase 0 で `claude -p` が起動不能・hook が headless で発火しない・コストが想定を大きく超える、のいずれかが判明した場合: **その時点で停止しユーザーに報告**。subagent ロールプレイ運転（忠実度低下を明示）への切替はユーザー判断を仰ぐ。

## 8. 除外範囲（やらないこと）

- Web 競合調査のやり直し（2026-06-10 の調査を流用）
- 発見した欠陥の修正・進化テーマの実装（分離原則）
- フルスケール成果物（複数ページ・複数機能）の作り込み
