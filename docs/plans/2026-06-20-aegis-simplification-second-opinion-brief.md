## A. Aegis とは

Claude Code ネイティブの運用フレームワーク（hooks / gates / skills / STATUS ファイル）。
**開発・運用の知識が乏しい人が、AI ハーネスに *導かれる* ことで、堅牢なソフトを作って運用できる**
ようにするのが仕事。

## B. North Star（設計目標・不変）

**「知識の無い人でも、ハーネスに *従って進むだけで*、クライアント課題を上流の設計 → 実装 →
運用後の改善まで解決しきれる。ハーネスに導かれていること自体が正しいゴール到達になる。」**

- **操作的なバー**: あるステップが *人間に dev/運用の知識を要求する* なら、それは「ハーネスの穴」。
- **配布モデル**: end user は *封印された* Aegis を **消費する**（内部を編集しない）。内部は
  作者＋AI が保守する。→ **内部の複雑さは「end user から封印され、AI が保守できる」限り許容**。
  *利用者に露出する表層*の複雑さは不可。
- **LLM進化レンズ**: LLM が賢くなるほど、ハーネスは *薄く* なるべき（目標は不変）。

## C. 判断ルール（親基準 / master cut-line）

各機構について問う:
> **「この機構が壊れる/無くなって検知に失敗したとき、*知識の乏しいユーザーが静かに騙される*か?
> しかも *他に安全網が無い* か?」**
- **Yes** → 残す（ただし *機能する最も薄い形* で）。ユーザーを守るので。
- **No**（作者自身のミスを捕まえるだけ／他のチェックで既にカバー）→ **cut または統合**。

判定の語彙: **keep-thin / rebuild / delegate-to-AI / cut**。

## D. 対象の3機構（コードベースから検証済みの事実）

### M2 — test-strength-drill
約455行のミューテーションテスト機構（＋約491行・28ケースのテスト）。QA ゲート承認時に、*変更
された行* にバイト単位の改変（例 `>=`→`>`）を当てて、テストコマンドを再実行する。改変しても
テストが緑のまま（mutant が生き残る）ならゲートを落とす。**未コミットの変更がある通常の
プロダクトコードでは動く。** ただし *フレームワーク自身* のタスクには構造的に適用不能——その
コードは QA ゲートが走る前に既にコミット済み（working-tree diff が空＝改変する行が無い）。なので
フレームワークタスクでは明示的に skip（監査される skip＋理由＋手動4-mutant のフォールバック）。
fail-closed。低 churn。**目的**: ユーザーのテストが本当にバグを捕まえるか（緑on緑でないか）を検証。

### M3 — skill_behavior_manifest
部分文字列の存在チェッカー。ハードコードされた表（7 skill → 14個の「重要な指示文字列」。例: tdd
skill は今も「テストなしのプロダクションコードは禁止」を含むこと）。手動スクリプトが各 skill
ファイルにその文字列がまだ在るか確認し、欠けていれば落とす。**どの hook/CI にも繋がっていない
——手動実行。配布/インストール先のプロジェクトには manifest ファイルが同梱されず、チェックは
そこでは一切走らない。** 自認している限界（コードコメント）:「これは *事故的な* 削除を捕まえる。
指示文とその manifest トークンを *同じコミットで両方* 消す確信犯は素通り——壁ではなく速度バンプ」。
skill の文言が正当に変わるたびトークン表の手動更新が要る。実行コストは安い。**目的**: judgment
skill が核の指示を静かに失うのを止める。

### M4 — observation / fingerprint hooks
PostToolUse フックが **すべての Bash コマンド** を追記型の evidence log に記録し、テスト実行を
git の「worktree fingerprint」（HEAD＋変更/未追跡のコードファイルのハッシュ。docs は除外）に
束ねる。ゲート承認時、判定カードは「最新のテストランナーの記録の fingerprint＝現在の worktree
fingerprint」かつ「本物のテスト要約マーカーを観測した」ときだけテストを 🟢 緑にする。それ以外は
🟡 未検証（静かに通れない）。これにより **AI が「テスト通った」を実際に走らせず自己申告するのを
止める**。脅威モデル: 事故防止（署名ではなくハッシュ＝意図的なログ改竄には耐えない）。コスト:
**全 Bash コマンドで** python3 を約2プロセス＋ fingerprint 計算の git サブプロセスを起動。実際に
消費されるのはテストランナーの記録だけなのに *無条件に* 払う。fail-open（セッションを壊さない）。
**目的**: ゲートのテスト判定を、AI の自己申告でなく *観測された実行* に基づかせる。

## あなたへの依頼

M2 / M3 / M4 それぞれについて、独立に:
1. **判定**（keep-thin / rebuild / delegate-to-AI / cut）
2. **理由**（3〜4文。親基準を明示的に適用: 無くなったら *誰が* 静かに騙されるか? 他に安全網は?）
3. **確信度**（低/中/高）

その後:
- **見落としている観点**: 親基準の枠組みが取りこぼしている点（どの機構でも）。
- **親基準の誤適用チェック**: 親基準を素朴に読むと *間違った* 答えになる機構はどれか、なぜか。

合計 ~450 語以内。「場合による」で逃げず、必ず判定を1つにコミットすること。

**【重要】あなた自身の判定を書き切るまで、次の「セクションE」は読まないでください（盲検維持）。**

## E. 答え合わせ（自分の判定を確定してから開くこと）

Aegis 側（作者＋その AI）の現時点の判定はこうです。あなたの判定と一致したか、しなければどちらが
正しいか、根拠を添えて述べてください:

- **M2 = keep-thin（維持）**。理由: ユーザーは自分でテストの「強さ」を検証できない。緑なだけで
  誤った安心を得る。これを補う他機構は無い（M4 はテストが *走った* ことは示すが *弱さ* は見ない）。
  framework タスクで skip するのは構造的縁ケースで、ターゲット用途（未コミットのプロダクト
  コード）では機能する。＝誤診で「過剰」ではない。
- **M3 = cut / 統合**。理由: 配布先では走らない（封印側）＝守るのは *作者の編集事故* だけで
  end user ではない。自認の限界（同コミットで素通り）で作者にとっても信頼できる網ではない。
  ハードコード表は LLM 進化で *厚く* なる方向＝North Star と逆。腐っても *緑のまま* で false
  assurance を生む。要求（skill が機能し続ける）は本物だが、git＋編集時 AI レビューへ委譲が筋。
- **M4 = rebuild（保証は維持・コストをホットパス外へ）**。理由: AI の自己申告を止める＝知識の
  乏しいユーザーを直接守る最強の検証で、他に代替なし＝機能は必須。ただし保証はゲート時にあるのに
  全 Bash コマンドで重い計算を払うのは純粋な無駄。テストランナーのコマンドだけ／ゲート時の遅延
  計算に寄せれば、保護を保ったままコストを落とせる。重いハーネスはユーザーに hook を切らせ、
  安全網そのものを消す二次被害もある。

特に **M3 を本当に cut すべきか**、**M4 を rebuild と呼ぶべきか（単なる微調整でなく）** に、
あなたの独立した見解を聞きたい。
