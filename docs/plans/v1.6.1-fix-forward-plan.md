### Task 1（C-1）: control-plane 変数展開バイパスを封鎖

**blockedBy:** なし | **モデル:** `opus`（security critical）
**ファイル:** 対象 `hooks/check-control-plane.sh:46-100` / テスト `tests/test_control_plane_var_expansion.py`（新規）
**意図:** 現状の regex はリテラル `hooks/` を探すため、変数展開で構築した path（`$D/lib/emit.sh` 等）が allow になる。redirect operator (`>`, `>>`, `tee`) 以外にも `sed -i`, `cp`, `mv`, `install`, `dd of=`, `truncate`, `python -c "open(...)"` 等、ファイルを書く utility は多数。**単純な「assign＋redirect」ヒューリスティクスでは捕捉漏れが残る**ため、より広い検知に倒す。
**検知ロジック（最終案）:** 以下 2 段で判定する。
- **段 1（fast-path 維持）**: 現状の literal `hooks/` / `scripts/` / `.claude/` 検査は維持（既存の正常系を割らないため）。ヒットしたら従来通り deny。

**TDD:**
1. **失敗テスト（必須 deny/ask）** — 以下 9 PoC が全て deny または ask（`{}` allow ではない）:

### Task 2（C-2）: テスト緑色偽装を封鎖

**blockedBy:** なし | **モデル:** `opus`（security critical）
**ファイル:** 対象 `scripts/build-judge-card.py:185-215` ＋ `hooks/post-bash-observe.sh` ＋ `hooks/lib/patterns.sh` / テスト `tests/test_test_runner_realness.py`（新規）
**意図:** 現状は test-runner regex に match しさえすれば `status:ok` → `green`。`pytest --version` / `--collect-only` / `-h` / `bash -c "pytest -h; echo PASS"` などはランナー名は出るが**テスト 0 件**で抜ける。「output に `passed` を含む」レベルのマーカーは `echo "1 passed"` で再偽装可能。**正確なサマリ行**を fail-closed で要求する。

**マーカー仕様（patterns.sh 単一所有）:** `AEGIS_TEST_PASS_MARKER_REGEX` を追加。各ランナーの**最終サマリ行**のみ拾う:
- `pytest`: `^=+ \d+ passed(?:,| in )` または `^=+ \d+ failed,` （summary line）
- `unittest`: `^Ran \d+ tests in \d+\.\d+s` ＋ `^OK\b` または `^FAILED\b`
- `jest`: `^Tests:\s+(?:\d+ failed,\s+)?\d+ passed`
- `vitest`: `^\s*Test Files\s+\d+ passed` または `^\s*Tests\s+\d+ passed`
- `cargo`: `^test result: ok\.` または `^test result: FAILED\.`
- `go`: `^ok\s+\S+\s+[\d.]+s` または `^FAIL\s+`
- `npm/yarn/pnpm/bun test`: 内部で jest/vitest/mocha のいずれかを呼ぶため、上のいずれかの marker を流用

**Schema migration:** 直接ログ payload に sdout を保存する代わりに、**post-bash-observe.sh が boolean `marker_verified` フィールド**を evidence-log entry に追加する。読み手側は `marker_verified=true` のときだけ green / red を返す。フィールド不在エントリ（v1.6.0 以前）は強制的に `unverified` 化（schema 互換規則は「Schema Migration」章を参照）。

**TDD:**
1. **失敗テスト（必須 unverified）** — 以下 8 偽装が全て `unverified`:
   - `pytest --version` （summary line なし）
   - `pytest --collect-only` （`collected` のみ）
   - `pytest -h`
   - `pytest -k __NEVER_MATCH__` （`no tests ran` summary、現マーカー集合では unverified）
   - `npm test --dry-run`
   - `pytest --co -q tests/x; echo "1 passed"` （文字列偽装、summary 形に当たらない）
   - `bash -c "pytest --version; echo '=== 1 passed in 0.0s'"` （wrapper／v152 で既に unverified だが念のため）
   - `echo "===== 1 passed in 0.0s"` （ランナー名すらない → 段 1 で runner regex miss → unverified）
2. **正常系テスト（必須 green）** — 以下が `green`:
   - `pytest tests/`（出力末尾に `===== 3 passed in 0.42s` summary line）
   - `pytest -q tests/test_x.py`（`====== 1 passed in 0.01s`）
   - `npm test`（出力に `Tests:       5 passed, 5 total`）
   - `python3 -m unittest discover tests`（`Ran 17 tests in 89.6s` ＋ `OK`）
3. **実装方針**:
   - patterns.sh に `AEGIS_TEST_PASS_MARKER_REGEX` 配列を追加
   - post-bash-observe.sh は tool_response.output の末尾 4KiB から marker regex を試走し、いずれかに hit すれば `marker_verified:true` を entry に追加
   - build-judge-card.py の `read_test_result` は entry に `marker_verified:true` がなければ強制的に `unverified`
   - patterns 二重実装防止: bash 側と python 側で同じ regex を読むよう `_test_pass_marker_patterns(root)` を新設（既存 `_test_runner_patterns` と同じ source 経由）
**受入条件:**
- 8 偽装すべて `unverified`
- 4 正常パターンすべて `green`
- 既存の `tests/test_test_runner_*` / `test_extractors.py` の挙動は維持

### Task 3（C-3）: client_ready_for_dev の touch バイパスを封鎖

**blockedBy:** なし | **モデル:** `opus`
**ファイル:** 対象 `scripts/check_status.py:471-476` ＋ `scripts/update-gate.sh`（承認時呼出） ＋ `templates/PRD.template.md` / `SCOPE.template.md` / `NFR.template.md` / `ACCEPTANCE.template.md` / `HANDOVER-TO-DEV.template.md` / `TRANSLATION-MAPPING.template.md` / テスト `tests/test_client_ready_artifact_content.py`（新規）
**意図:** 現状は 6 ファイルの**存在のみ**を見る。0 バイト OK で `touch` 1 行承認可能。「最小バイト + 自然言語見出し grep」だと template の見出しを変更したら CI が壊れるか、または見落として touch バイパスが再発する。**machine-readable sentinel コメントを template に埋め込み**、check_status は sentinel を grep する。

**sentinel 仕様:** 各テンプレ末尾に HTML コメントで挿入:
```html
<!-- aegis-required-section: prd-context -->
<!-- aegis-required-section: scope-in-out -->
<!-- aegis-required-section: nfr -->
<!-- aegis-required-section: acceptance-criteria -->
<!-- aegis-required-section: handover-to-dev -->
<!-- aegis-required-section: translation-mapping -->
```
ユーザはテンプレをコピーした後、内容を埋めた上で sentinel コメントを**残す**ことが要件。content を消すと sentinel も消える運用にする（テンプレの末尾固定位置に置くため）。

**検査ロジック:**
- 6 ファイルそれぞれについて「(a) ファイル存在 && (b) 最低 200 バイト && (c) 対応する sentinel コメントを含む」の 3 条件 AND
- いずれか欠落で deny（gate approve 拒否）。**完了時にも再走**（task-completed hook が evidence-integrity で同じ検査を実施）→ approve 後の content 削除を検知

**TDD:**
1. 失敗テスト: 6 ファイル touch（0 バイト・sentinel なし）で承認 → **deny**
2. 失敗テスト: 6 ファイル 1 KiB あるが sentinel コメントを削除 → **deny**
3. 失敗テスト: 6 ファイル sentinel あるが 100 バイト → **deny**（最小バイト要件）
4. 正常系: テンプレ初期コピー（sentinel あり・初期 prose で 200B 超）→ **approve**
5. 既存テンプレ末尾に sentinel を追記（テンプレファイルを編集）
6. 既存の advisory（`current_refs.translation` 空）は維持
7. 完了時検査: gate approve 後に PRD.md から sentinel を削除 → `check-task-completed.sh` が deny

- 既存 `client_ready_for_dev` 関連テストが PASS

## Schema Migration（evidence-log: marker_verified フィールド追加）

Task 2 で `hooks/post-bash-observe.sh` が evidence-log の各 entry に boolean `marker_verified` フィールドを追加する。

**後方互換規則:**

| ログ世代 | `marker_verified` | `read_test_result` の返り値 |
|---------|-------------------|---------------------------|
| v1.6.0 以前（フィールド不在） | `null`（不在） | 強制的に `unverified`（fail-closed） |
| v1.6.1 以降・偽装系 | `false` | `unverified` |
| v1.6.1 以降・本物テスト | `true` | `status:ok` なら `green`、`fail` なら `red` |

**マイグレーション:** 次回テスト実行で entry が上書きされるまでは旧 entry は `unverified` 化。v1.6.0 ログを持つプロジェクトは「テストを再実行して claims を更新」する必要がある（v161-deploy-checklist.md に明示）。

**契約テスト:** `tests/test_test_runner_realness.py` で「marker_verified 不在の合成エントリ → unverified」と「marker_verified:false → unverified」と「marker_verified:true + status:ok → green」を 3 ケースとして固定。

## 受容済みリスク（v161-security.md 草案）

v1.6.1 時点で**意図的に受容**するリスクを計画段階で前出しする。

1. **`git stash push .env`**: 誤検知頻発（個人開発で .env を一時退避する正当用途）のため deny しない。stash 経由の意図的漏洩は v1.6.2 以降で限定 deny を検討
2. **`eval`／`alias`／`cat .env > config` 経由の漏洩**: 構造的に regex では塞げない（v1.5.2 受容済みと同じ系統）
3. **Task 1 段 2 ヒューリスティクスの誤検知**: 「変数代入＋未展開変数＋書込み token」を満たす正当 build script が ask に倒れる可能性。ask は user 承認で逃がせる＝productivity への影響は許容範囲
4. **Task 2 marker regex の false-negative（マイナーランナー）**: meson test / ctest / phpunit 等は marker 集合外なので `unverified` 化。`record-test-result.py`（信頼ランナー）経由を案内
5. **Task 5 の数値契約テスト brittleness**: 自然文中の数値を grep するためコメント追加で偽陽性可能性。v1.7 で `<!-- count:* -->` sentinel 方式または auto-generation に移行する宣言

すべて fail-open ではなく fail-safer（unverified／ask）方向。green 偽装や deny 緩和には繋がらない。

## リスク

- **R1: Task 1（変数展開封鎖）の誤検知**: 通常の `MY_VAR=foo make build` を deny に倒すと開発者の生産性が下がる
  - 対策: 案A は「変数代入＋書込みリダイレクト」の AND 条件で絞る。書込みリダイレクトのない代入は allow。誤検知が出たら user-fixable な `ask` に倒す（直接 deny にしない）
- **R2: Task 2（テストマーカー要求）の false-negative**: マイナーランナー（meson test, ctest 等）の出力フォーマットがマーカーに当たらず unverified 化
  - 対策: マーカー集合に `^ok\b` / `not ok` / `Test result:` / `Ran \d+ tests` を含める。マイナーケースは `record-test-result.py` 経由（信頼ランナー）を案内
- **R3: Task 3（最小バイト＋見出し）の互換性破壊**: 既存プロジェクトが既に旧形式で承認済みの場合、再承認で deny される
  - 対策: 既に `approved` 状態のままなら content 検査をスキップ。新規 approve 時のみ強制
- **R4: Task 4（matcher に resume 追加）の hook 二重発火**: `--resume` で SessionStart が走る分、初期化が二重実行される可能性
  - 対策: `session-start.sh` は冪等性をすでに持つ（snapshot 存在チェック）。テストで二重発火しても矛盾しないことを assert
- **R5: Task 5（doc 契約テスト）の維持コスト**: 数値契約は hook を増やすたびに doc も更新が必要
  - 対策: それが**目的**。CI で必ず気づく状態にする。v1.7 で自動生成化（T2）まで進めば負担消滅
- **R6: 9 タスクを 1 PR に bundle するリスク**: review が大きくなり、1 タスクの reject で全体が遅延
  - 対策: Task 0/4/5/8 は独立に commit 化、Task 1/2/3 は独立だが security critical なので grill-code を強める。1 PR でも commit 単位で revert 可能な粒度を維持
