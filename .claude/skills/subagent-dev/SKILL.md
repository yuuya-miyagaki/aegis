# サブエージェント駆動開発

> タスクごとにフレッシュなサブエージェントを起動し、2 段階レビューで品質を保証する。

## いつ使うか

- 承認済みの実装計画があるとき
- タスクがおおむね独立しているとき
- コンテキスト汚染を防ぎたいとき

## コアルール

1. **タスクごとにフレッシュなサブエージェント** を起動する
2. サブエージェントには **該当タスクの情報だけ** をインラインで渡す（計画全文
   ではなく、そのタスクのセクションのみ）
3. 各タスクの完了後、**2 段階レビュー** を実施する
4. 両方のレビューが合格してからタスクを完了マークする
5. **レビュー/検証系サブエージェント**（Step 3/3.5/4 の reviewer 系）の委譲プロンプトには routing.md「Verification delegation」の6拘束（核＝read-only・tree 変更禁止）を含める

## プロセス

### Step 0: 準備

1. 計画ファイルを読み、タスク一覧を把握する
2. 各タスクの依存関係を確認する
3. 全タスクをタスクリストとして整理する（必要なら TaskCreate を使用。session-local のサブタスク管理のみ。セッション横断の状態は STATUS.md）

### Step 0.5: 共通ユーティリティの抽出

計画を読む際に、複数タスクで重複しそうなヘルパーを特定する:

検出パターン:
- 「取得して 404 なら例外」→ `findXOrThrow` 系
- 「権限チェック」→ `assertRole` 系
- 「入力バリデーション」→ `validateX` 系

該当がある場合:
1. Task 0（共通ユーティリティ）をタスクリストの先頭に追加
2. 後続タスクの blockedBy に Task 0 を設定
3. 後続タスクはインポートして再利用する

### Step 1: 実装サブエージェントの起動

サブエージェントに渡す情報:
- 該当タスクのセクション（意図、ファイル、受入条件、インターフェース）
- 対象ファイルのパス
- TDD ルール: 「テストを先に書け。失敗を確認してから実装せよ」

**渡さないもの:**
- 計画の全文（該当タスク以外のセクション）
- セッション履歴
- 不要なプロジェクトドキュメント

### Step 2: サブエージェント完了後の対応

サブエージェントの結果を確認し、以下の判断を行う:

- **正常完了**: Stage 1 レビューへ進む
- **懸念あり**: 懸念が正確性・スコープに関わるなら対処。観察のみなら記録して
  進む
- **コンテキスト不足**: 不足情報をコーディネーターが補足して再起動
- **ブロック**: 原因を評価する。コンテキスト不足 → 追加。推論不足 → より能力
  の高いモデルで再起動。タスクが大きすぎる → 分割。計画の問題 → ユーザーに
  エスカレート

### Step 3: タスク単位レビュー

各タスクの実装直後に reviewer エージェントを起動する。ここでのレビューは
**task-level review** であり、そのタスクが計画どおりか、局所的なコード品質に問題
がないかを確認する。

**レビュー深度はサブタスクの変更ファイル件数で決定する:**

| 変更ファイル件数 | Stage 1（仕様準拠） | Stage 2（コード品質） |
|-----------------|-------------------|---------------------|
| 1 ファイル | 必須 | 省略可（スキップ理由を記録） |
| 2-5 ファイル | 必須 | 省略可（スキップ理由を記録） |
| 6+ ファイル | 必須 | 必須 |

※ ここでいう「変更ファイル件数」は STATUS.md の `task_size` ではなく、
そのサブタスクが実際に変更したファイルの数を指す。

Stage 1 は `.claude/agents/reviewer.md` の仕様準拠レビューに従う。
Stage 2 は同 agent のコード品質レビューに従う。

**結果:**
- 該当 Stage すべて PASS → タスク完了マーク → 次のタスクへ
- いずれか FAIL → 実装サブエージェントが修正 → 再レビュー

### Step 3.5: Review Army（specialist 並列レビュー）

phase-level review（Step 4）の前に、変更の性質に応じて specialist reviewer を並列起動する。

**起動判断（diff-scope 分析）:**

| 変更の特徴 | 起動する specialist |
|-----------|-------------------|
| テストファイルの変更あり、またはテストなしの実装あり | reviewer-testing |
| ループ/クエリ/API呼び出しの変更あり | reviewer-performance |
| 3ファイル以上の変更、または新モジュール追加 | reviewer-maintainability |

**ルール:**
- 該当しない specialist は起動しない（コスト節約）
- specialist は Task tool で並列起動する
- 各 specialist の finding には confidence score（1-10）を付与する
- confidence 7 未満の finding は注意書き付きで報告する
- 全 specialist の結果を統合し、重複を排除してから phase-level review に進む

### Step 4: review フェーズの最終レビュー

- 全タスク完了後、**phase-level review** を 1 回実施する
- ここではタスク個別レビューの再実行ではなく、変更全体が計画・仕様・evidence と
  整合しているかを確認する
- `docs/qa-reports/` に最終レビュー記録を残し、`phase = review` の完了判定に使う
- `docs/STATUS.md` を更新する

## モデル選択指針（トークン節約）

コストと品質のバランスを取るため、タスクの性質でモデルを選ぶ:

| タスクの性質 | モデル | 根拠 |
|---|---|---|
| 機械的な実装（1-2 ファイル、明確な仕様） | `sonnet` | 仕様が明確でも下限は sonnet（haiku 不使用） |
| 統合・判断が必要（複数ファイル連携） | `sonnet` | パターンマッチングと調整力が必要 |
| 設計・レビュー | `opus` | 判断力が品質に直結 |

サブエージェント起動時に Task ツールの `model` パラメータで指定する。

## 並列実行ルール

- **同一ファイルを変更するタスクの並列実行は禁止**（コンフリクト）
- **共有可変資源**（テスト DB・ポート・グローバル状態）で衝突するタスクの並列起動も禁止
  （実測: 並行 integration テストが同一テスト DB を TRUNCATE し合い偽 fail。
  vitest の fileParallelism:false はプロセス内のみ有効）
- 標準運用: integration テストを実行するタスクは同時に起動する1バッチにつき 1 体まで
  （unit のみのタスクと組む）。代替: per-agent の DB/スキーマ分離
- ファイル競合がない独立タスクは並列実行可（worktree 分離を推奨）
- 並列実行時もレビューは各タスク個別に実施する

## Red Flags（禁止事項）

- 計画全文をサブエージェントに渡さない（該当タスクだけ渡す）
- Stage 1 は全サブタスクで必須。Stage 2 省略は変更 5 ファイル以下のみ、スキップ理由の記録が必要
- task-level review と phase-level review を同一のものとして扱わない
- 未修正の問題がある状態で次のタスクに進まない
- サブエージェントの質問を無視しない
- ブロック時にそのまま同じモデルでリトライしない

## コンテキスト予算

- コーディネーター（親セッション）は計画の全体像を保持する
- 各サブエージェントは自分のタスクの情報だけを受け取る
- レビュー結果は簡潔な要約のみコーディネーターに返す
